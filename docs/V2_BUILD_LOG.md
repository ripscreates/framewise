## 2026-10-18 — Product direction clarified

- **Product model:** Framewise is a graphical guide and wrapper for FFmpeg's command-line program. The guided UI selects capabilities and builds ordinary FFmpeg flags; the desktop app should show the exact command, explain it, and run it with the user's desktop FFmpeg. Users should retain a way to copy the command for the terminal and inspect logs/results.
- **Keep both editions:** the browser edition remains the cross-platform web app and keeps its browser-compatible engine. The native Mac edition should invoke the real desktop FFmpeg executable. Share the workflow and command-building model where practical, but keep execution behind a platform-specific engine boundary.
- **Technology direction:** keep the current React/TypeScript UI. Use the existing Tauri 2 shell (Rust) to launch FFmpeg as a native sidecar/child process, passing an argument vector rather than evaluating a shell command string. FFmpeg itself is mainly written in ISO C11, with platform-specific assembly for performance; it is not a Rust project. Rust belongs in the desktop wrapper and process/filesystem bridge, not as a replacement for FFmpeg.
- **Version strategy proposed:** pin a known stable FFmpeg build in each Framewise release. Later, add a signed/checksummed engine manifest and an app-managed version selector so users can check for a new compatible build, install it, and switch/roll back independently. FFmpeg's official project distributes source code and points to third-party executable builds; a distributable Framewise binary therefore needs a deliberately chosen, auditable build source/configuration and matching notices/source materials.
- **Release information checked:** the official FFmpeg download page lists 9.0.2, released 2026-09-18, as the latest stable release on the 9.0 branch at the time of this entry.
- **Codec/licensing issue found:** the current workflow uses `libx264` for H.264 output. FFmpeg documents GPL-licensed optional components and states that enabling GPL parts changes FFmpeg's license to GPL; its compliance guidance also calls for auditing enabled external libraries and the exact binary configuration. The Mac package cannot be called a verified LGPL-only build while retaining this encoder without changing the build/configuration. Decide whether the first Mac build should bundle a GPL-enabled FFmpeg distribution with its required compliance materials, or keep an LGPL-compatible build and revise/limit encoder choices. Framewise's own source license and FFmpeg's binary obligations must be documented separately.
- **Recommended first milestone:** get one architecture-specific Mac beta working end to end with the native process, file dialogs/drop, batch execution, progress/cancel, output location, and command/log history. Make the bundled FFmpeg version visible. Add in-app FFmpeg replacement only after the project has a verified build pipeline and secure update manifest; update the Framewise shell through Tauri's separately signed app updater.
- **User decision — platform:** the first native beta targets Apple Silicon Macs. Linux and Windows are possible later ports after the Mac edition is stable.
- **User decision — engines:** bundle a pinned FFmpeg build and let users choose between it and a compatible FFmpeg already installed on their Mac. Framewise should check the chosen build and adapt its available options/command profiles to that build. The user also approved the separate engine upgrade strategy.
- **Local environment check:** `/opt/homebrew/bin/ffmpeg` is available on the Apple Silicon development host. It reports FFmpeg 9.0.2, Homebrew build configuration `--enable-gpl`, and includes the currently used `libx264`, `libvpx-vp9`, `libmp3lame`, `aac`, VideoToolbox H.264, and required filters (including `subtitles`, `palettegen`, `paletteuse`, `loudnorm`, `crop`, and `scale`). This was a capability inspection only; no media conversion was run. This local Homebrew binary is a useful system-engine candidate for development, not automatically a suitable redistributable bundle.
- **Recommended engine selection:** bundle and select Framewise's pinned, tested FFmpeg build by default so every guided command has a known capability baseline. On first launch, optionally discover a system `ffmpeg` and report its version/build configuration and relevant encoders, muxers, filters, and protocols. Offer it as an explicit alternate engine only after capability checks; never silently replace the bundled default. Version string alone is insufficient because builds of the same FFmpeg release can include different codecs and filters.
- **Upgrade workflow:** engine update checking should compare the bundled pinned build against Framewise's own signed/checksummed release manifest. The manifest should identify version, macOS architecture, build configuration, enabled codecs/filters, license notices, checksum, and source/build recipe. Keep current and previous engine versions available for rollback. Tauri's separate updater handles Framewise app releases; it does not by itself update the FFmpeg child process.
- **Documentation and command compatibility:** when developers change the bundled FFmpeg version or build configuration, update the supported-engine matrix, codec/feature metadata, command explanations, build recipe, and legal notices as part of that release. Run a command smoke-test matrix against the new pinned binary before calling that engine supported. A user's optional system FFmpeg can trigger an in-app compatibility report; it should not rewrite the project's documentation.
- **Still open before packaging:** confirm the LGPL-compatible + VideoToolbox route after validating command and output behavior; decide whether V2 includes editable custom flags in its first beta.

## 2026-10-18 — Development Mac FFmpeg and distribution risk review

- **Host:** macOS 15.7.7 on an Apple M1 Max (`arm64`); Homebrew is installed under `/opt/homebrew`.
- **Installed engine:** `/opt/homebrew/bin/ffmpeg`, Homebrew `ffmpeg 9.0.2_1`; the executable is an arm64 Mach-O. `ffmpeg -license` reports GNU GPL version 3 or later, and local Homebrew formula metadata reports GPL-3.0-or-later.
- **Build profile:** the executable reports `--enable-gpl`, `--enable-libx264`, `--enable-libx265`, `--enable-libvpx`, `--enable-libmp3lame`, `--enable-libopus`, and `--enable-videotoolbox`, among other options. It has the encoder/filter capabilities used by current Framewise workflows. It also exposes `h264_videotoolbox`.
- **Portability:** `otool -L` shows links to Homebrew-managed FFmpeg libraries and dependencies under `/opt/homebrew/Cellar` and `/opt/homebrew/opt`. This installed Homebrew tree is a useful optional system engine on this Mac, but copying its `ffmpeg` executable alone would not create a self-contained app bundle.
- **Recommendation for least licensing risk with H.264 output:** build a separate, pinned FFmpeg bundle from the official source with GPL and nonfree components disabled, audit every enabled external dependency, and enable Apple's VideoToolbox H.264 path plus FFmpeg's native AAC encoder. Keep `libx264` as a capability of compatible user-selected system builds. Framewise must generate an engine-specific H.264 command profile because x264's CRF/preset options do not map directly to VideoToolbox's rate-control options. Verify actual output quality, playback, and fallback behavior before release.
- **Risk boundary:** FFmpeg's own LGPL guidance recommends builds without `--enable-gpl` or `--enable-nonfree` for an LGPL distribution and calls for matching source, build configuration, and notices. This reduces GPL packaging burden but does not settle separate codec-patent questions. The current web edition also loads `@ffmpeg/core@0.12.10`, whose package metadata is already documented in the README as GPL-2.0-or-later; audit its distribution independently from the new native binary.
- **Inspection limits:** `ffmpeg -version`, `-license`, `-buildconf`, `-encoders`, `-filters`, encoder help, and `otool -L` were inspected. No media was converted. The Homebrew metadata refresh could not reach `formulae.brew.sh` because DNS was unavailable; installed binary output and the locally available Homebrew information were still readable.
